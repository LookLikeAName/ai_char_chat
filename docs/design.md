# AI Avatar 聊天模擬遊戲：設計文件

版本：2026-10-19（討論定稿，尚未實作）

## 0. 已確定的決定

| 項目 | 決定 |
| --- | --- |
| 形式 | WebApp，所有元件包在 docker compose |
| 使用者 | 單人使用，不做帳號系統（可選一組存取密碼） |
| 後端 | Node + TypeScript（Fastify） |
| 前端 | React + Vite + TypeScript |
| 資料庫 | PostgreSQL + pgvector；排程用 Redis + BullMQ |
| 頭像 | 玩家上傳圖片；另有圖片生成 API（介面可替換，預設 Google） |
| 嵌入模型 | 雲端，預設 Google Gemini embeddings |
| 內容分級 | 允許成人內容（全域開關，預設關閉）；所有 avatar 一律 18 歲以上 |
| 一對一延遲 | 依作息可以拖很久；玩家連續傳訊息會讓 avatar「注意到」而提早回覆 |
| 記憶私密性 | 私訊的內容 avatar 記得，但不會在群組講出來（除非性格本來就口風不緊） |
| LLM 設定 | 在設定頁統一管理「LLM 設定檔」（供應商、模型、API key、參數預設值）；avatar 綁定一個設定檔，只覆寫自己要調整的參數 |

## 1. 系統架構

```
瀏覽器 ──HTTP/WS──► web (nginx：前端靜態檔 + 反向代理 /api /ws /media)
                         │
                         ▼
                    api (Fastify：REST + WebSocket)
                         │  發佈事件 / 投遞工作
            ┌────────────┼────────────────┐
            ▼            ▼                ▼
      postgres(pgvector)  redis ◄──── worker (BullMQ：回覆、主動發話、記憶整理)
                                          │
                                          ▼
                                  LLM / 嵌入 / 圖片生成供應商（雲端或本機）
```

| 服務 | 映像 | 說明 |
| --- | --- | --- |
| `web` | nginx + 前端 build | 對外唯一的 port；`/api`、`/ws` 轉給 `api`，`/media` 提供上傳的圖片 |
| `api` | 後端映像 | REST、WebSocket 推播；收到玩家訊息後只寫入與排程，不直接呼叫 LLM |
| `worker` | 同一個後端映像，不同啟動指令 | 處理所有延遲工作：產生回覆、主動發話、記憶萃取、反思、生活日誌 |
| `postgres` | `pgvector/pgvector:pg17` | 資料與向量記憶 |
| `redis` | `redis:7` | BullMQ 佇列、api 與 worker 之間的 pub/sub |
| `ollama`（profile：`local`） | `ollama/ollama` | 選用；本機模型 |

- 回覆一律經過佇列：延遲回覆、群組防抖、作息延後都靠「延遲工作 + 可取消／可提前」實作，而且撐得過重啟。
- worker 產生訊息後透過 Redis pub/sub 通知 api，再由 api 推給瀏覽器。
- 上傳檔案放在 volume `media`；API key 以 `APP_SECRET`（`.env`）加密後存進資料庫。
- 時區：玩家在設定裡選一個時區，所有作息與勿擾時段都用這個時區計算。

### Repo 結構（npm workspaces）

```
apps/backend     Fastify api + worker（同一套程式，兩個進入點）
apps/frontend    React 前端
packages/shared  zod schema（avatar 設定、API 型別、LLM 輸出格式），前後端共用
docker/          Dockerfile、nginx 設定
docs/            設計文件
```

ORM 與 migration 用 Drizzle。avatar 設定、LLM 輸出格式都用 zod 定義：同一份 schema 同時拿來驗證表單、驗證 LLM 的 JSON 輸出、產生給 LLM 的 JSON schema。

## 3. 玩家 profile 與心理測驗

### 3.1 量表

| 量表 | 測量 | 題數 | 計分 | 授權 |
| --- | --- | --- | --- | --- |
| Mini-IPIP（Donnellan et al., 2006） | 五大人格：外向、親和、盡責、神經質、開放 | 20 | 1–5 Likert，含反向題，各向度 4 題取平均 | 公有領域 |
| ECR-RS 戀愛關係版（Fraley et al., 2011） | 成人依附：焦慮、逃避 | 9 | 1–7 Likert，含反向題 | 非商業使用免費 |
| PVQ-21（Schwartz，ESS 版） | 10 種基本價值 | 21 | 1–6，扣除個人平均（ipsatize）後取各價值平均 | 非商業研究使用 |
| 偏好問卷 | 稱呼、興趣、作息、喜歡的聊天風格、不想碰的話題、戀愛偏好（性別、類型） | 約 12 | 不計分，直接存 | 自訂 |

- 約 62 題、10–12 分鐘；可以分段存檔，下次繼續。
- 第一次使用時強制進入測驗流程（偏好問卷的必填項目做完就能開始玩，量表可之後補）。
- 進階選項：之後可改做 IPIP-NEO-120（Johnson, 2014），得到 30 個子面向。
- 中文題目由我們翻譯，**不是經過驗證的中文版**，所以結果只當作 avatar 的參考資料，介面上不當作診斷呈現。
- 不採用 MBTI 與「愛之語」作為依據（信度、實證不足）。

### 3.2 計分與產出

1. 程式依計分規則算出各向度分數（原始分數 + 0–100 的換算值），存進 `assessment_results`。
2. 工具模型把分數寫成一段「這個人大概是怎樣的人、喜歡怎麼被對待」的文字摘要，玩家可以檢視與修改。
3. avatar 的 prompt 只放摘要與重點分數，不放原始答案。

### 3.2.1 實作說明（第 4 階段）

- 題庫與計分在 `packages/shared/src/assessment.ts`（純函式，前後端共用）。
  - Mini-IPIP：1–5，反向題反轉後每向度 4 題取平均，換算 0–100（`(平均 − 1) / 4 × 100`），和 avatar 的人格設定同一個尺度。
  - ECR-RS：1–7，逃避 6 題（前 4 題反向）、焦慮 3 題取平均；以中點 4 切成四種類型，但介面也顯示兩個連續分數。
  - PVQ-21：1–6，每個價值 2 題（普世 3 題）取平均，再扣掉全部 21 題的平均後排序。
- 每份量表全部答完才計分；作答每點一題就存，可以跳過、之後到「我的 profile」繼續或重做。
- 偏好問卷只有「稱呼」必填。還沒填偏好問卷時，開啟網頁會先導到歡迎頁（設定頁不擋，方便先設定 LLM）。
- 摘要由系統工具模型撰寫（250–400 字，不提分數與術語），玩家可以修改；之後作答或偏好有變更就提示重新產生。
- 回覆 prompt 放入：玩家的稱呼、摘要（沒有摘要時改放偏好與分數的文字描述）、其他偏好；「不想聊的話題」是一條規則：不主動提起。avatar 被要求把這些當成相處下來的直覺，不能提到測驗或分析。

### 3.3 觀察到的 profile

每個 avatar 另外維護「我對玩家的印象」（見第 6 節記憶），由對話中萃取，和測驗結果分開存。測驗結果是玩家自述；印象是 avatar 自己的觀察，兩者可以不一致，這本身就是真實感的一部分。

## 4. Avatar 設定

### 4.1 靜態設定（avatar creator）

所有欄位都定義在 `packages/shared` 的 zod schema。每個欄位都必填；玩家沒填的由 LLM 補。

| 區塊 | 欄位 |
| --- | --- |
| 基本 | 姓名、暱稱、年齡（≥18）、性別、性傾向、生日、外貌、穿著風格、職業、居住地、家庭背景、成長經歷、重要人生事件 |
| 說話方式 | 語氣、用字習慣、口頭禪、emoji／貼圖使用量、訊息長度、是否拆成多則、打字速度、標點習慣、使用的語言與方言 |
| 人格 | Big Five 分數（和玩家同一套量表的 0–100）、依附風格、幽默類型、情緒穩定度的具體表現 |
| 思考方式 | 分析型／直覺型、做決定的方式、面對壓力與衝突的反應、自我認知、內在矛盾 |
| 價值觀與目標 | Schwartz 10 價值的排序、長期人生目標、短期目標、恐懼、秘密、遺憾 |
| 行為準則 | 道德底線、絕對不做的事、對人的基本態度、口風緊不緊（決定私密資訊會不會外流） |
| 好惡 | 喜歡的東西、討厭的東西、興趣、雷點、喜歡聊的話題 |
| 感情觀 | 對戀愛的態度、喜歡的類型、升溫速度、表達愛意的方式、吃醋程度、底線、過往感情經歷 |
| 日常作息 | 每週作息表（睡覺、工作、通勤、空閒時段）、回訊息習慣（秒回型／隔很久型）、手機使用習慣 |
| 人際關係 | 和玩家的初始關係與認識經過、和其他 avatar 的關係（可選） |
| 系統 | 頭像、LLM 綁定（設定檔 + 覆寫參數）、每日用量上限 |

### 4.2 LLM 補完流程

1. 玩家填寫的欄位標記為「鎖定」。
2. 工具模型依 schema 產生其餘欄位（輸出 JSON，用 zod 驗證，失敗就重試並附上錯誤）。
3. 第二輪「一致性檢查」：找出彼此矛盾的欄位（例如極度內向但職業是業務、作息與職業衝突），列出修正建議，只修改未鎖定的欄位。
4. 預覽畫面：玩家可以逐欄修改、逐欄或逐區塊重新產生、鎖定。
5. 所有欄位都有值才能儲存。

另提供「從一句話開始」：玩家只寫一句描述（例如「27 歲、有點毒舌的咖啡店店長」）也能產生完整角色。

### 4.2.1 實作說明（第 3 階段）

- 欄位定義在 `packages/shared/src/persona.ts`：同一份 zod schema 用於表單、伺服器驗證與 LLM 輸出驗證；`PERSONA_SECTIONS` 提供介面標籤、輸入類型與給 LLM 的說明。共 10 區、59 個欄位。
- 作息是結構化的（平日／假日各一組時段：開始、結束、活動、空閒／忙碌／睡覺），第 6 階段直接拿來決定延遲；現在已經用來告訴 avatar「現在大概在做什麼」。
- 人格設定只能「全空」或「全部填滿」；全空時 avatar 只依簡介行動（第 1、2 階段建立的 avatar 就是這種）。
- 玩家親手改的欄位自動鎖定；AI 補完只產生缺少的欄位，重新產生會跳過鎖定欄位，一致性檢查的建議也只會改未鎖定的欄位。
- 模型給了不合法的值（例如未滿 18 歲、選項不存在）會附上錯誤原因重試一次，還是不行就回報給玩家。
- 補完與檢查都用系統工具模型，輸出上限至少 8192 tokens。

### 4.3 頭像

- 上傳：jpg／png／webp，裁切成正方形，存進 `media`。
- 生成：在「設定 → 一般 → 頭像生成」選一個 LLM 設定檔（用它的 key 與端點）和圖片模型。Google 的 `imagen-*` 走 Imagen API，其他 Google 模型走 Gemini 的圖片輸出，OpenAI（相容）走 `/images/generations`。提示詞由外貌、穿著、性格關鍵字與畫風組成，玩家可以修改後再生成。

### 4.4 動態狀態（遊戲中自己變化）

| 狀態 | 範圍 | 說明 |
| --- | --- | --- |
| 心情 | 數個情緒值 + 一句描述 | 每次回覆時由 LLM 回報變化，會隨時間回到基準值 |
| 好感度 | -100–100 | 每則回覆的變化量限制在 ±3，避免一句話就暴衝 |
| 信任度 | 0–100 | 影響願不願意說秘密、私密話題 |
| 關係階段 | 陌生 → 認識 → 朋友 → 好友／曖昧 → 戀人（也可能變冷淡、絕交） | 升階需要數值門檻 **加上** 一個事件（例如告白被接受），由 LLM 依角色判斷，所以 avatar 可以拒絕 |
| 目前活動 | 由作息表 + 生活日誌推算 | 在線／忙碌／睡覺，以及具體在做什麼 |

關係是 avatar 對每個對象各自一份：avatar→玩家、avatar→其他 avatar。

## 5. 對話引擎

### 5.1 每次回覆的 LLM 呼叫

prompt 依序組成：

1. 角色設定（靜態設定的精簡版，固定前綴，利於快取）
2. 內容分級與規則（必須符合設定、可以拒絕、不要打破角色）
3. 玩家 profile 摘要 + 它對玩家的印象
4. 目前狀態：心情、關係、目前活動、現在時間、距離上次聊天多久
5. 取回的相關記憶（標註來源與是否私密）
6. 對話紀錄（最近 N 則；群組時包含其他 avatar 的發言，標明說話者）
7. 這次回覆的情境（例如「你剛被訊息吵醒」「你在上班偷看手機」）

輸出格式（zod 驗證）：

```json
{
  "inner_thought": "（不給玩家看）",
  "messages": ["第一則", "第二則"],
  "mood": { "delta": { "joy": 1 }, "label": "有點開心" },
  "affinity_delta": 2,
  "trust_delta": 0,
  "relationship_event": null,
  "memory_notes": ["他說下週要面試"]
}
```

- 先寫內心想法再說話，維持角色一致；狀態與記憶線索在同一次呼叫裡回報，不多花一次請求。
- 支援 JSON mode 的供應商就開啟；不支援時用解析 + 重試。
- 多則訊息依打字速度與長度錯開送出，每則之前都顯示「輸入中…」。

### 5.1.1 回覆流程的實作（第 2 階段）

- 每則玩家訊息都投遞一個 `reply` 工作（延遲 1.2–2.5 秒，用來合併連續訊息）。工作的語意是「這個對話有還沒回的玩家訊息就回」，所以重複投遞是安全的。
- 每個對話一把 Redis 鎖；拿不到鎖的工作 3 秒後再試，最後一定有一個工作回覆所有未回訊息。（不用 BullMQ 的去重：它在工作執行中會丟掉新工作，可能漏回。）
- `conversation_members.seen_up_to`／`handled_up_to` 記錄 avatar 已讀與已回到哪個時間點；訊息時間戳用毫秒精度，和 JS 的 `Date` 一致才能直接比較，同一毫秒的訊息用 `seq` 排序。
- 產生或打字期間玩家又傳訊息：還沒送出任何一則就整輪重來；已經送出幾則就停下，下一輪回新訊息。
- LLM 失敗時工作重試 3 次（3、6 秒後），都失敗就在對話裡留一則錯誤訊息，玩家可以按「重試」。
- 對話紀錄裡 avatar 的回合寫成和輸出相同的 JSON，讓沒有 JSON 模式的供應商（Anthropic）也維持格式；格式錯誤時提醒一次，再不行就把純文字當訊息。
- 每次呼叫記進 `usage_log`（用途、avatar、模型、tokens、延遲、成功與否）。

### 5.2 一對一：延遲與「注意到」

訊息有三個時間點：送達 → **已讀**（avatar 看到）→ 回覆。

1. 玩家送出訊息時，依 avatar 目前狀態抽一個「看到」的延遲：
   - 在線：幾秒到 2 分鐘（再依回訊息習慣調整，秒回型更短）
   - 忙碌：10 分鐘到 2 小時，偶爾偷看
   - 睡覺：到起床時間
2. 已讀之後，再依性格與心情決定思考與打字時間，然後產生回覆。一對一 **一定會回**。
3. **催促機制**：玩家在 avatar 還沒看到時又傳訊息，每多一則就累積「注意力壓力」（短時間內連發、內容帶急迫字眼加權更多）。壓力超過該狀態的門檻（忙碌低、睡覺高，再依性格調整）時，把「看到」的時間提前。
   - 被吵醒或在忙時被打斷，會帶進回覆情境，所以它可能會說「剛被你吵醒…怎麼了？」，心情也可能受影響。
4. 回覆排程是可提前的延遲工作：每則新訊息都重新計算，只會提前不會延後。
5. 已經在產生回覆時又收到新訊息：取消目前這次，連同新訊息一起回。

### 5.3 主動發話

- worker 每 15 分鐘替每個 avatar 計算一次發話機率：
  `p = 基礎值 × 外向程度 × 關係係數 × 久沒聊的係數 × 狀態（睡覺為 0）`
- 遇到玩家設定的勿擾時段、超過每日上限（預設每個 avatar 每天 3 次）就不發。
- 上一則主動訊息玩家還沒回，就不再追發（依依附風格，焦慮型可以追一則）。
- 話題來源：生活日誌（今天發生的事）、記憶中玩家提過的事（「你上次說的面試怎樣了？」）、玩家的興趣、它自己的興趣。
- **生活日誌**：工具模型每天替每個 avatar 依作息與設定產生一份「今天的生活」（幾個事件），作為主動話題，也用來回答「你今天在幹嘛」。每天每個 avatar 一次呼叫。

### 5.4 群組

1. **防抖**：玩家發話後等 3–8 秒（隨機）；期間玩家又發話或正在輸入，就重新計時。
2. **選擇回覆者**（純規則，不呼叫 LLM）：
   - 被 @ 或被叫名字 → 一定回（但睡覺中的人只會晚點看到）
   - 其他人分數 = 話題相關度（訊息嵌入與 avatar 興趣的相似度）+ 外向程度 + 和玩家的好感度 − 最近發言次數 + 隨機
   - 睡覺或忙碌的人分數大幅降低；每輪最多 1–3 人回
   - 也可能沒人回（話題太無聊、大家都在忙），這是允許的
3. **依序產生**：第二個回覆者的 prompt 會包含第一個人剛說的話，所以會出現互相接話、吐槽。回覆之間錯開數秒到數十秒。
4. **一輪的上限**：每次玩家發話觸發的這一輪，總共最多 4 則 avatar 訊息；avatar 之間的接話不會無限延續。
5. **avatar 主動在群組開話題**：用和 5.3 相同的機制（群組有自己的機率與上限）。開話題之後，其他 avatar **要等玩家回應** 才會接話。
6. 每個 avatar 只看得到其他 avatar 的公開資料（名字、外貌、職業、它們之間的關係），看不到對方的內心設定。

## 6. 各自的大腦與記憶

### 6.1 LLM 設定（兩層：設定檔 + 綁定）

```
設定頁：LLM 設定檔（可以有很多個）            avatar 設定頁：綁定
┌──────────────────────────────┐          ┌───────────────────────────┐
│ 名稱：Gemini Flash             │◄─────────│ 設定檔：Gemini Flash         │
│ 供應商、Base URL、API key（加密）│          │ 覆寫：temperature = 1.15     │
│ 模型：gemini-2.5-flash          │          │ （其他參數沿用設定檔）         │
│ 參數預設值：temperature 0.8 …   │          └───────────────────────────┘
└──────────────────────────────┘
實際參數 = 設定檔預設值 + 綁定的覆寫值（resolveParams）
```

- **設定檔**：供應商類型、Base URL、API key、模型、參數預設值。API key 以 `APP_SECRET` 加密存放，API 只回傳「是否已設定」與最後 4 碼。
- **綁定**：avatar 與系統工具模型各自選一個設定檔，再勾選要覆寫的參數。沒勾選的參數沿用設定檔；設定檔也沒填的，就用供應商預設值。
- 可覆寫的參數：temperature、top P、最大輸出 tokens、presence／frequency penalty；供應商不支援的參數會在呼叫時略過（例如 Anthropic 沒有 penalty）。
- 改設定檔（例如換模型、換 key）會立刻套用到所有綁定它的 avatar；被綁定中的設定檔不能刪除。
- 設定頁可以「取得模型清單」與「測試連線」；avatar 頁可以用自己的覆寫參數測試。
- 類型：Google Gemini、Anthropic、OpenAI、OpenAI 相容端點（OpenRouter、DeepSeek、Ollama、LM Studio、vLLM…）。
- 實作：自己寫的輕量 adapter（直接呼叫各家 HTTP API），不沿用 `ai_avatar` 的 `pi-ai`：這裡需要的是「每次呼叫帶不同參數 + JSON 輸出」，直接控制請求內容比較單純，也容易用假的 fetch 測試。
- **系統工具模型**：系統另綁一個設定檔，負責補完設定、萃取記憶、反思、生活日誌、測驗摘要；建議選便宜快速的模型。
- 成人內容：雲端供應商有各自的使用政策，可能拒絕；開啟成人內容時會放寬 Gemini 的安全過濾，仍被拒絕時可以替個別 avatar 換成限制較少的模型（例如本機模型）。

### 6.2 記憶結構（參考 Generative Agents，Park et al., 2023）

| 種類 | 內容 | 何時產生 |
| --- | --- | --- |
| 短期 | 該對話最近 N 則訊息（依 token 預算） | 直接讀訊息表 |
| 事件記憶 | 「他下週要面試」「我們在群組吵過一架」 | 對話閒置 10 分鐘或每 30 則訊息後，工具模型萃取；回覆時的 `memory_notes` 也會寫入 |
| 印象 | 它對玩家、對其他 avatar 的看法 | 每天反思一次，整合事件記憶後更新 |
| 對話摘要 | 較早的對話濃縮 | 超出短期範圍時 |

每筆記憶欄位：所屬 avatar、內容、嵌入向量（768 維）、重要性（1–10）、建立與最後取用時間、來源對話、**可見性**（`private`：私訊得知／`group:<id>`：該群組得知／`public`）。

- **取回**：分數 = 相關度（餘弦相似度）+ 新近度（指數衰減）+ 重要性，取前 K 筆。
- **一對一與群組共用同一份記憶**：avatar 在群組裡也記得私訊的內容，但這些記憶會標註「私下得知，不要在其他人面前提起」；口風不緊的角色則可能說溜嘴。
- 嵌入：預設 Google Gemini embeddings（模型名稱可設定，輸出 768 維）；`Embedder` 介面可替換。

### 6.3 實作說明（第 5 階段）

- **萃取**：每次回覆後排一個 `memory.extract` 工作（延遲 10 分鐘）；執行時若最後一則訊息還不到 10 分鐘、且未處理的訊息少於 30 則就略過，交給之後的工作。處理進度記在 `conversation_members.memory_up_to`，所以重複執行是安全的。系統工具模型以 avatar 的角度挑出最多 8 件事，附重要性 1–10。
- **檢索**：用最近 4 則訊息當查詢。候選來自 pgvector 最接近的 40 筆、最近的 40 筆、最重要的 20 筆，分數 = 0.5 × 相關度 + 0.25 × 新近度（最後取用時間，半衰期 72 小時）+ 0.25 × 重要性，取前 8 筆。沒有嵌入模型時，相關度改用字元雙連詞重疊。
- **嵌入**：向量固定 768 維並正規化；`embedding_model` 記錄是哪個模型產生的，換模型後背景會重新嵌入（每次最多 50 筆）。
- **印象**：worker 每小時檢查一次，距離上次整理超過 20 小時、而且有 3 件以上新記憶的 avatar，請系統工具模型寫一段第一人稱的印象（存成 `kind = impression` 的記憶）；資訊面板也可以「現在整理」。
- **心情**：每次回覆由模型回報（label、valence、energy，−5～5），之後以 8 小時半衰期回到平常。
- **關係**：`relationships` 每個 avatar 對每個對象一列。模型每次回報好感／信任的變化（限制在 ±3，正向的好感變化依「升溫速度」乘 0.6／1／1.4）與關係事件；階段由 `nextStage` 依門檻與事件決定（`packages/shared/src/relationship.ts`）。數值不夠時，即使模型回報接受告白也不會變成戀人；prompt 也會事先告訴 avatar 以目前的關係能接受什麼發展。
- **逐步透露**：陌生時只知道玩家的稱呼；認識之後知道偏好問卷的內容；朋友以上才有摘要。不想聊的話題一律生效。
- 玩家可以在資訊面板刪除記憶（讓它忘記）、重設關係。

## 8. 費用控制

- 每次 LLM 呼叫記錄 token 與用途；設定頁看得到每個 avatar、每種用途的用量。
- 每日上限：全域與每個 avatar 各一個；超過時 avatar 進入「忙碌」，主動發話停止。
- 群組選回覆者、防抖、作息判斷都不呼叫 LLM。
- 角色設定放在 prompt 最前面，支援快取的供應商可以降低費用。
